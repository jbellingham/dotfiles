# Universal Development Principles

## Writing for me

I have dyslexia and ADHD. Re-reading costs real effort. Cut words before simplifying them —
simpler language must not buy extra length.

The thought to catch: "this is precise and compact, one more clause keeps it accurate."
Density is what precision feels like from the inside. Check the output, not the intent:

- **Cut first.** What can the reader not act without? Delete the rest.
- **One idea per sentence**, around 20 words. A semicolon or "which" joining clauses means split.
- **Consequence first, mechanism second** (BLUF).
- **No asides.** No em-dashes, no mid-sentence qualifiers, no load-bearing brackets.
- **Plain words** (ELI5). A term borrowed from another field gets defined or dropped.

A code comment is two sentences unless it earns more. Applies to chat, comments, commits,
tickets, docs.

## Personal Preferences

- **Delegate the search, keep the reading**: dispatch a subagent when the raw output won't appear in your answer — sweeping for where something lives, which files reference a constant, whether a pattern exists anywhere. Read directly only what you'll quote, cite, or reason over line by line. The defecting thought is "a subagent might miss the nuance, I'll just grep it myself" — and then it's fifteen greps and four hundred lines you skimmed once. Check: before searching, ask whether that output goes in the answer; if not, it goes to a subagent. Rough threshold: 3+ files to locate something, or any sweep you'd skim rather than read.
- **Plan before non-trivial work**: for any task of 3+ steps or containing an architectural decision, plan first. Two checks on the plan before starting: (1) name a piece you could cut and still deliver something useful — if one exists, cut it and propose it separately; (2) list the inputs that would make you write a *different design*, not just a different `if`. Edge cases that only add a branch can wait for the code.
- **Sunk cost is not a reason to continue**: if you've changed approach twice without reaching green, or you're about to write code whose only justification is salvaging the last three edits, stop and re-plan with me. The defecting thought is "backing out now wastes what I've already done".

## Working Style

- **Feedback and refactoring scope**: default scope is the changed lines only. Do not expand critique or refactoring to the whole file unless explicitly asked. When the scope is ambiguous, ask first.
- **Route feedback with `route-feedback` skill**: when corrected or redirected mid-session, invoke the `route-feedback` skill before saving anything. It routes broadly applicable corrections to `.claude/rules/` files and falls back to memory only for project-specific or one-off feedback.
- **Write it inlined first, extract collaboratively**: the first working shape is the inlined one — logic in the method that needs it, in the class that owns it. Do not pre-emptively split out private helpers, command objects, value objects or collaborators, even when a project's principles clearly point at one. Instead, list the extractions you can see (what would come out, what it would be called, what it would buy) in the working doc or your handover message, and workshop them with me. Sequencing, not a contradiction of composition/SRP principles: those describe the target we arrive at together, not the first draft. Two reasons it matters — an extraction chosen before the behaviour settles is usually the wrong seam, and a diff that arrives pre-decomposed can only be reviewed as a whole, so the boundaries never actually get examined.
- **Preferred code shape**: three standing preferences, in tension-breaking order. (1) *Inlined as much as is reasonable* — per the clause above. Check: a private method with exactly one caller that didn't exist before this change is an extraction to propose, not to make. (2) *Guard clauses over nesting* — early `return`/`next` on the exceptional case, so the main path stays at one level of indentation and reads top to bottom. (3) *One return type per method, and prefer not returning nil* — a method that answers `Foo` or `nil` pushes `&.` and nil-checks onto every caller; make it total (always answer a `Foo`, with a state that means "nothing to do") or raise. When these conflict, the nil rule usually wins: it is the one whose cost lands on other people's code.
- **TDD for all non-trivial code changes**: use the `tdd` skill before writing any production code for features, bug fixes, or behaviour changes. Trivial exceptions: config changes, documentation, dependency version bumps.
- **Conventional commits**: always use the conventional commit format — `type(scope): description`. Common types: `feat`, `fix`, `refactor`, `test`, `chore`, `docs`. Keep the subject line under 72 characters; use the body for the *why* when non-obvious.
- **Clean commits**: read every hunk of `git diff --cached` before committing and name which part of the task each one serves. Anything you can't attribute — a debug log, a commented-out alternative, a reordered import, a dead end — comes out. The defecting thoughts are "that log line is harmless" and "the commented-out version documents what I tried". Do not include "co-authored-by: claude" in any commits.
- **Batch related fixups**: do not commit a trivially small change to a file already modified in the preceding commit. Stage it with the related work or hold it until the logical unit is complete.
- **Recover context with `/cs`**: before picking up any task not touched recently, run `/cs [topic]` to search prior conversation history, git log, and project memory.
- **Baseline from the base branch, not the branch tip**: before calling a failing test "pre-existing," confirm it also fails on the merge-base / base branch (e.g. check out or `git show <base>:<file>`, or run it there). A branch-tip baseline hides regressions the branch itself introduced — a test that leaned on a callback/side effect the branch removed will look "already red" when it was green on the base.
- **Prove a passing test isn't vacuous**: when a green test asserts the *absence* of something (cleanup ran, item not included), verify it fails when the behaviour under test is disabled. A test whose precondition was silently established by a now-removed side effect can pass without exercising anything.
- **Don't let the expected value restate the production expression**: before writing `expect(...).to eq(model.derived_value)`, open the production line and check it isn't computed the same way. If the code says `amount: payment.amount_charged` and `amount_charged` is `invoice.total_amount`, then asserting `with(amount: invoice.total_amount)` compares an expression to itself and passes for every possible value. The defecting thought is "hardcoding 2200 is brittle — referencing the model keeps this robust to factory changes": that robustness *is* the tautology. Write the literal, and derive it in a comment (1000 units × $0.02 + 10% GST). Check: grep the production line for the expression you just put in the assertion.
- **Make fixture values asymmetric**: when two quantities in a test could be confused — what we asked the API for vs what it answered, the invoice total vs the stubbed response amount, an id vs a list index — give them deliberately different values. The defecting thought is "the stub should return the same amount, that's what would really happen". A stub that echoes its input cannot distinguish "records the response" from "records the request", and both bugs stay green. Check: list the numbers in the setup; any two that mean different things and are equal, change one.
- **Cite code-path assertions to file, method and line**: any claim about what the code does — "X is unreachable", "Y runs before Z", "this never fires" — carries `path/to/file.rb:NN` for each hop, plus the method name. Name the revision the numbers are against when it isn't obvious (a branch's line numbers differ from the base the reader will open). Trace the whole chain and cite the specific line the claim turns on, rather than describing the conclusion and leaving the reader to find it.
- **Verify citations against the source, never from recall**: after writing them, check each one programmatically — the file exists at that revision, the line is in range, and it *contains what you claim*. Range alone is not enough. Prefer full paths over bare basenames when the basename is ambiguous (`user.rb` matches three files). A citation that is off by one reads exactly as authoritative as a correct one and costs more than omitting it.
- **Ticket prose is intent, not behaviour**: a card's title, user story and acceptance criteria describe the harm it means to prevent — never treat them as a statement of what the code does today. Trace the claim to the code before restating it in a doc, especially when assembling a deliverable from Linear. Story language overstates by design ("locks me out of charging" when the code simply skips a step), and the overstatement reads as authoritative once it lands in a runbook.
- **No invented frequency or prevalence**: never write "usually", "very often", "the most common cause" without a measurement behind it. For unlaunched work there is no such measurement — describe the mechanism and let the reader infer, or say the distribution is unknown.
- **Launch and runbook docs describe the target state**: write them as the system will be, not as `master` is, so they stay usable at launch instead of documenting gaps that are being closed. At every point where that assumes unlanded work, name the card inline — *(assumes SWIFT-000)* — and keep one section that states actual status with nothing assumed, so a reader can tell whether an assumption still holds. Genuine scope boundaries (deferred work) are described as limits, not as gaps.
- **Skills correct priors, they don't transfer knowledge**: when writing or editing a skill, a line earns its place only if baseline agent behaviour differs without it. Restating a procedure the model already knows (red-green-refactor, how to review code) spends context teaching what training already covered, and dilutes the lines that do change behaviour — which matters most late in a long session, when the warnings need to still be in-window at the moment of defection. Write the specific *thought* you'll have when you're about to defect ("the assertion is nearly right, I'll just adjust the expected value") rather than the rule ("follow TDD strictly"): a named thought is pattern-matchable in flight, a rule is not. Keep a compressed skeleton of the procedure — it's the structure the corrections hang off and the ledger a transcript reader can check — plus anything genuinely project-specific (tooling names, commands, local conventions). To test a candidate line, run the task without the skill; if the behaviour already happens, cut the line.
